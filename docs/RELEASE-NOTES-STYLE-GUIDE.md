# Release 文案规范（v1.14.0 起）

> **状态：已否决（2026-10-23）。不要按本文档的 A/B/C 分类写发布文案。**
> 发布文案继续沿用 v1.13.0 的统一格式：分端「变更内容」+「What's Changed」提交短链 +「下载与校验」+ Full Changelog。

> 按版本性质分三类，写法和长度都不同。判断顺序：先看是否修后端 Bug，再看是否是纯前端。

## A 类：大版本（`1.X.0`）

用户能感知到的新功能、跨端契约变化、行为变化都归这类。照 v1.13.0 的骨架写全。

结构：

1. `# SillyClient vX.Y.Z`
2. `>` 摘要：三端各一句，各端点明改了什么
3. `## ⚠️ 重要提醒`：仅在存在数据风险、跨版本不兼容、必须手动操作时保留，放在摘要下
4. `## 变更内容`：共享节标（Windows / Android / iOS），再 `**Windows**` / `**Android**` / `**iOS**` 三节
5. `## What's Changed`：按 Windows / Android / iOS / 通用前端顺序贴真实提交短链
6. `## 下载与校验`：小写 SHA-256 加文件名，三行分开列，末尾三条安装说明
7. 三端 Full Changelog 链接

摘要写法：用冒号引出各端改动，不写「三端同版更新」这类空话，参考 v1.13.0 的「Windows：取消默认存储位置，修复升级后实例失联与误装顶替」。

变更条目写法：冒号后直陈事实，不解释用户感受，不加「依旧」「已经」「会更好」。数字、路径、按钮名直接给全，不复述实现过程。

## B 类：紧急修复（`1.X.Y`，Y 小）

修的是崩溃、数据丢失、功能不可用、发热卡死这类问题。受影响的人需要立刻知道要不要更新、更新前要做什么。

结构：A 类的第 1、2、3、4、6 项，去掉 What's Changed。

摘要第一句必须写清问题是什么、影响谁。例如：

```text
> 紧急修复。Android：新建实例在部分机型上会卡在「依赖完整性校验未通过」导致创建失败，本版修复该问题。Windows 与 iOS 无此问题。
```

`## ⚠️ 重要提醒` 用在需要用户手动操作时，例如「更新前请先导出实例」。

条目里写清三点：原来的表现、现在的表现、未更新用户受影响的范围。不写做了什么重构。

## C 类：纯前端更新（`1.X.Y`，Y 小）

只同步通用前端，未动后端、存储、导入导出、实例管理链路。1.13.1 属这类。

结构：

1. `# SillyClient vX.Y.Z`
2. `>` 摘要：三端各一句
3. `## 变更内容`：共享节标（Windows / Android / iOS），再 `**Windows**` / `**Android**` / `**iOS**` 三节，每节 1 到 3 条
4. `## 下载与校验`：同 A 类
5. 三端 Full Changelog 链接

不写 What's Changed。提交短链对前端小版本没有意义，Full Changelog 链接已经够。

摘要里写「本版只更新前端界面，未改动实例创建、存储、导入导出等链路」，让不敢升级的人放心。共享节控制在 5 条内，每节 1 到 3 条，全文不超过 40 行。

条目写法同 A 类：冒号后直陈事实，写用户看到的变化，不写实现方式。

## 三类都不写

- 「后端零改动」这类内部口径，用户不关心后端
- 测试通过数、编译结果、日志排查过程
- 「体验更好」「更加流畅」这类主观描述，要写具体变化
- 修复过程的排查描述，只写原来的表现和现在的表现
